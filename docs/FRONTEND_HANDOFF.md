# AUSNOX — FRONTEND HANDOFF
Version: 1.0 | 2026-11-14 | Branch `feat/frontend-fable`

This document describes what the frontend phase built, what it deliberately did not build, and how the scientific-engine phase plugs in. Statuses use **PASS / FAIL / BLOCKED / NOT RUN** as required by AGENT_GUIDELINES.md.

> **Integration update (2026-11-15).** On `integration/ausnox-mvp` the real adapters are implemented on `@ausnox/scientific-engine` and real mode is the default; the mock adapters described here remain available with `VITE_DATA_MODE=mock` (`npm run dev:mock`) and back the unit/UI tests. Contracts were extended (slope-unknown validity, ground distance, slope-limited snap, verification info, tile bounds, layer caveats, sample missions) and the map now uses a Mars equirectangular CRS. This document is kept as the record of the frontend phase; current status is in `docs/INTEGRATION_REPORT.md`.

**Read this first:** the app runs on **mock adapters**. No NASA or USGS dataset is downloaded, validated or displayed. The terrain is a synthetic analytic surface, routes are demonstration arcs and daylight times are fixed examples. Every such value is labelled *Illustrative* in the UI. The scientific gates in TESTING_AND_VALIDATION.md (S1–S5, R1–R4, M1–M3, D1, D2) remain **NOT RUN**. P0 of the product is therefore **not complete**; the P0 *frontend* is.

## 1. Architecture and directory structure

Static-first single-page app: React 19, TypeScript 6 (strict, `noUncheckedIndexedAccess`), Vite 8, Tailwind CSS 4, Radix UI primitives in shadcn-style wrappers, Zustand 5, Leaflet 1.9 + React Leaflet 5, Recharts 3, Lucide icons. No backend, no router dependency (views sync to the URL hash), no environment variable needed to run.

~~~text
src/
  app/App.tsx                     root: bootstrap, view switch, global dialogs, footer disclaimer
  components/
    layout/      TopBar, HelpDialog, Panel, Section, Stat, StatusAlert, EmptyState, Logo
    map/         MarsMap (Leaflet), MapChrome (tools, legend, coordinate bar, placement banner,
                 coordinate-entry dialog, imagery notice), LayerControls
    planner/     MissionBlocks (feasibility headline, route comparison, margin breakdown, violations)

    charts/      ElevationProfile, TerrainHistogram

    mission-control/     Workspace (map + side panels + dock), MissionStatusPanel
~~~

`components.json` is present so further shadcn/ui components can be added with the CLI. The existing `ui/` components were written by hand on Radix primitives in the shadcn conventions (cva variants, `cn`), not generated by the CLI.

## 4. State management

Five Zustand stores, all shared state is read from them (no duplicated literals in components):

- `dataStore`: terrain manifest and raster, layers, waypoints, per-layer imagery state, load errors.
- `missionStore`: mission config, calculation status, `stale` flag, results for **both** route modes, solar result, validation issues. Any edit marks results stale, aborts the in-flight request and schedules a recalculation (550 ms debounce). Responses carry a `requestId`; superseded ones are discarded. Switching route mode needs no request.
- `simStore`: simulated seconds, playing, speed. Never reads a real clock for mission time.
- `uiStore`: view, placement mode and refused-placement state, inspected cell, layer visibility, provenance drawer, sheets.
- `mapStore`: pointer hover sample and zoom, isolated so pointer moves do not re-render panels.

## 5. Implemented interactions

View switching; opening and closing sheets, dialogs and the provenance drawer; placing habitat, destination and stops by map click or typed coordinates (grid metres or nominal lon/lat); explicit confirm-to-snap for unsupported cells; choosing waypoints as destination or stops; adding and removing stops; editing science durations; route mode switch; route comparison with optional second route on the map; advanced assumptions (speed, slope limit, reserve, start time, warning threshold, daylight scenario, EVA limit) with range validation and restore-defaults; calculate and recalculate; load sample; reset; cell inspection; basemap, overlay and map-feature toggles; zoom, fit, pan; simulation start, pause, resume, reset, step ±5 min, scrub, speed, jump to event; demo failure scenarios.

## 7. Mock adapters

`src/services/adapters/mock/`. All deterministic; simulated latency is 420 ms (0 under test).

| File | Behaviour |
| --- | --- |
| `terrainField.ts`, `terrain.ts` | Fixed analytic surface on a 200 × 150 grid of 20 m cells (4 × 3 km): hill, ridge, bowl, scarp, two no-data pockets, footprint with two cut corners. Slope by nodata-aware finite differences. Manifest `status: 'illustrative-demo'`, georeference `kind: 'nominal-demo'`. |
| `mapData.ts` | Layer list: one available illustrative basemap (contour drawing), two illustrative overlays (elevation, slope), and HiRISE, CTX and MOLA basemaps listed as **unavailable**. Four illustrative waypoints with no geological claim. |
| `provenance.ts` | Source register taken from DATA_SOURCES.md. No NASA dataset is marked integrated. |
| `routing.ts` | Per segment, picks one of seven fixed arcs after sampling terrain every 10 m. Arcs touching missing data or exceeding the slope limit are discarded. Return leg chosen independently. **Not A\***; `terrainAwarePathfinding: false`. |
| `solar.ts` | Three fixed sunrise/sunset pairs. `mars24Validated: false`. |
| `mission.ts` | Timing and margin arithmetic from SCIENTIFIC_MODELS.md §5 and §7, constant speed. |
| `scenario.ts` | Demo failure scenarios: imagery offline, terrain missing, solar unavailable, routing timeout, no waypoints. Switched from the Data sources view. |

## 9. Integration entry points

Implement the factories in `src/services/adapters/real/index.ts`. Nothing else has to change.

- **Terrain** (`TerrainService`): load `public/data/jezero/manifest.json` and the grid, reject `SET_*` placeholders, expose `sample`, `nearestValid`, `toGeo`, `fromGeo` using the product CRS. Set `status: 'verified'` and `georeference.kind: 'verified'` only after gates S1–S3.
- **Map layers** (`MapDataService`): return `LayerImagery` of type `tiles` for Mars Trek WMTS. `MarsMap` currently uses `L.CRS.Simple` in grid metres; a real tile layer needs the Mars CRS and tile matrix configured there (see §12).
- **Routing** (`RoutingService.computeRoundTrip`): A\* per SCIENTIFIC_MODELS.md §4, ideally in a Web Worker. Honour the `AbortSignal`, echo `requestId`, set `terrainAwarePathfinding: true`, fill `samples` so the profile and simulation work.
- **Solar** (`SolarService.getSolarDay`): Mars24-derived sunrise and sunset at the given `GeoCoord`; set `mars24Validated: true` only after gate M1. `listScenarios` can map to dates or Ls values.
- **Feasibility** (`MissionService.assess`): the mock logic can be promoted once reviewed; it must keep returning `indeterminate` for missing inputs.

## 10. Error responses the UI handles

`ServiceError.code`: `NO_COVERAGE`, `NO_DATA`, `NO_ROUTE`, `UNSUPPORTED_SLOPE`, `INVALID_INPUT`, `TIMEOUT`, `MODEL_UNAVAILABLE`, `DATA_UNAVAILABLE`, `NOT_IMPLEMENTED`.

Mapping to feasibility: `UNSUPPORTED_SLOPE` and `NO_ROUTE` are known violations (infeasible). Every other route error, a missing route, or a missing or failed solar result is unknown (indeterminate). Terrain load failure blocks placement and calculation and shows an alert with retry. Imagery failure shows a notice with retry while terrain, routing and timing keep working.

## 11. Switching from mock to real data

~~~bash
cp .env.example .env.local   # then set VITE_DATA_MODE=real
npm run dev
~~~

With the current stubs, real mode shows unavailable states everywhere and no demo controls. Replace adapters one at a time; a mixed setup (for example real terrain with mock routing) can be composed in `src/services/index.ts`. `ResultSource.kind` drives the "Demonstration response" versus "Scientific engine result" wording, and `ProvenanceRecord.integration` drives the *Illustrative* badges, so the labels update from adapter data without UI edits.

## 12. Incomplete features

- No real NASA/USGS imagery or DEM; no Mars CRS or WMTS tile matrix in the map.
- No A\* routing, no Web Worker, no Mars24 solar model.
- No 3D explorer (P1). No mission JSON import/export (P1). No historical THEMIS or MEDA layer (P1).
- No local imagery fallback asset for provider outages.
- Stops cannot be reordered or renamed.
- Not deployed.

## 13. Known limitations

- Demonstration arcs can fail with `NO_ROUTE` where a real pathfinder would route around missing data.
- On-plan simulation keeps the return margin constant by construction; there is no off-plan model.
- Longitude and latitude shown are a nominal placement near Jezero, labelled "nominal", not a verified transform.
- A mission whose window crosses the sol boundary is drawn clamped at 24:00 on the timeline.
- One 1.05 MB JavaScript bundle (313 kB gzip); no code splitting yet.
- The Leaflet map is replaced by a stand-in in automated UI tests and was checked by hand instead.
- Colour contrast was chosen against WCAG AA by calculation; no automated accessibility audit or screen-reader session was run.
- The Figma file was viewed read-only in a browser. The floating-panel map composition, tool column, coordinate bar, clock and logo mark were carried over; the global feature list and full-orange basemap were not. No assets were exported from Figma; the logo mark was redrawn as an approximation.
